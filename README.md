# 服务健康监控

> 面向长期运行的定时任务/多进程系统：判断每个任务是真在跑、还是卡住了、还是压根没被触发。
> 输出不是一个 pass/fail，而是**带故障定位的分级判定**。

---

## 要解决的问题

一个跑了几个月的系统，最危险的失误是**以为它在跑，其实它停了**。

而且它不会报错——进程还在，端口还在监听，日志文件的时间戳甚至还在更新（因为别的模块在写）。

真实的坑，这几个都踩过：

| 现象 | 看起来 | 实际 |
|---|---|---|
| 端口有监听 | 服务正常 | **HTTP 502 是本地代理在替死上游**，服务早挂了 |
| 进程存在 | 在运行 | 加载的是旧代码，改文件对它无效 |
| 日志在更新 | 有活动 | 是另一个模块在写，这个模块停了 39 小时 |
| 面板在跑 | 全部正常 | **守护线程停了 10.65 小时**，面板自己不知道 |
| 某个任务没输出 | 没有信号 | 也可能**根本没被驱动**——这两件事在日志上长得一样 |

---

## 核心设计

### 1. 判定分级，不是一个布尔值

```python
# 返回 OK / LATE / MISSED / PANEL_DOWN / LEG_STALLED / GUARD_GAP
```

- `OK` 全部正常
- `LATE` 晚了但还在合理范围（可能这轮还没跑）
- `MISSED` 超时太久，基本判定漏跑
- `PANEL_DOWN` 面板进程不在
- `LEG_STALLED` 某个任务长时间没被驱动
- `GUARD_GAP` 守护线程在最近 24 小时里有 > 2 小时的空档

**为什么要分级**：`LATE` 不用管，`MISSED` 要补跑，`PANEL_DOWN` 要重启——处置完全不同。一个布尔值给不出处置方案。

### 2. 阈值全部有历史事故作为依据

```python
CLI_WARN_H = 26.0       # 略超正常上限：今天的轮次可能还没跑
CLI_FAIL_H = 30.0       # 漏跑一轮（历史上 39h、62.5h 两次都该 FAIL）
CACHE_FAIL_H = 30.0     # 行情缓存
GUARD_FAIL_H = 2.0      # 守护 30s 驱动，2h 没动 = 面板有问题
SPREAD_H = 6.0          # 各任务之间 age 极差超过它 => 有任务被漏掉
MARK_LAG_FAIL_D = 2     # 落后天数（>=2 天 = 漏一轮）
```

每条阈值后面都标了"为什么是这个数"，来自真实事故的时长。

**这是这个工具最值钱的地方**：不是随便定个 30 分钟，是从事故里量出来的。

### 3. 三个维度交叉，缺一个就会误判

| 维度 | 看什么 | 单独看的盲区 |
|---|---|---|
| 文件时间戳 | 这个任务多久没写文件 | 分不清"没被驱动"和"没有信号" |
| 心跳 | 守护线程是否还在跳 | 只能证明线程活着，不证明业务正常 |
| 进程/端口 | 服务是否监听 | 端口在 ≠ 服务正常（代理会替死） |

**三者要一起看**，任一维度单独都能给出错误结论。

### 4. 区分"没被驱动"和"没有输出"

这是最容易混的一对：

- 一个任务今天没有产生任何记录 → 可能是"正常，今天确实没触发的条件"
- 也可能是"轮次压根没跑，所以不可能有记录"

判法是看**驱动时刻**（谁在什么时候触发它），而不是看**记账时刻**（记录写在哪天）。

这两者混在一起，就会把"漏跑"误报成"正常"，或者反过来。

退出码也是分级的（0 正常 / 1 警告 / 2 需要处理），方便塞进定时任务里做自动告警。

## 怎么用

```bash
python health.py           # 人读报告（退出码 0/1/2）
python health.py --json    # 机器读（给告警系统）
```

纯标准库。退出码分级设计成能直接塞进定时任务：

```bash
python health.py || curl -X POST "$WEBHOOK" -d "服务异常"
```

演示快照里放了 7 个任务：4 个正常、2 个已停用、1 个漏跑。
跑一遍能看到「停用不报警」和「漏跑判 FAIL」同时生效。
`verdict()` 接受任意快照字典，接你自己的监控数据只需要拼好那个结构。

---

## 局限

1. 需要系统本身产出心跳/时间戳——没有这些信号就无从判断
2. 阈值是针对某套系统的运行节奏调的，换系统要重新标定
3. 只能发现"没跑"，不能发现"跑了但算错了"
